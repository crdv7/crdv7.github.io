## 前言

前一篇文章中讲到PostgreSQL 中进行删除和更新操作时，会产生无效的元组，需要对数据库进行定期的清理操作，这就是本篇文章所要介绍的 VACUUM 机制，这里主要介绍VACCUM的基本原理与流程。



## 正文

在 PostgreSQL 中，`VACUUM` 是一个非常重要的维护操作，用于回收因更新或删除操作而产生的“死元组”（dead tuples）所占用的空间，并优化表的性能。理解 `VACUUM` 的基本原理和执行流程，对于数据库管理员和开发者来说至关重要。

---

## 为什么需要 VACUUM？

PostgreSQL 使用多版本并发控制（MVCC）来管理并发事务。当用户对数据进行更新（UPDATE）或删除（DELETE）操作时，旧版本的数据并不会立即被删除，而是被标记为“死亡”状态，称为“死元组”。这些死元组会占用磁盘空间并可能影响查询性能。

如果不及时清理这些死元组，不仅会造成磁盘空间浪费（即“膨胀”），还可能导致查询效率下降，甚至索引失效等问题。

因此，PostgreSQL 提供了 `VACUUM` 命令来解决这些问题：

- 清理无效的 tuple；
- 回收页空间；
- 更新 `pg_class.relfrozenxid` 和 `pg_database.datfrozenxid`，防止事务 ID wraparound；
- （可选）更新表的统计信息（`ANALYZE`）；
- 对索引进行清理和重建（视参数而定）。二、VACUUM 的主要类型

### 1. `VACUUM`

这是标准的清理操作，通常是非阻塞的（不加锁）。它会扫描表，回收死元组占用的空间，并更新表的统计信息（如 `pg_stat_user_tables` 中的信息）。

```sql
VACUUM table_name;
```

### 2. `VACUUM FULL`

相比普通的 `VACUUM`，`VACUUM FULL` 更加强力，它会对表进行重新组织，将剩余的有效数据移动到表的前面，并释放后面的所有空闲空间。该操作会锁定表并在过程中重写整个表，因此代价较高。

```sql
VACUUM FULL table_name;
```

> `VACUUM FULL` 会消耗大量 I/O 和 CPU 资源，建议在低峰期执行。

### 3. `VACUUM ANALYZE`

此命令结合了 `VACUUM` 和 `ANALYZE` 操作，除了清理死元组外，还会收集表的统计信息，帮助优化器生成更高效的查询计划。

```sql
VACUUM ANALYZE table_name;
```

### 4. `VACUUM FREEZE`

主要用于防止事务 ID 回绕问题。在某些情况下（例如长时间不执行 `VACUUM`），事务 ID 可能循环使用，导致数据损坏。`VACUUM FREEZE` 会冻结旧的事务 ID，使它们不再变化。

```sql
VACUUM FREEZE table_name;
```

## VACUUM 的执行流程解析

以下是 `VACUUM` 执行的基本流程步骤：

### 启动 VACUUM 处理

- `VACUUM` 会对目标表加 **共享访问锁（ShareUpdateExclusiveLock）**，以防止冲突的结构性变更（如 `DROP`）。
- 根据需要选择是否处理索引（默认处理）。
- 初始化用于跟踪清理元组和页信息的相关数据结构。

###  扫描 Heap 表（主表）

- 对每个页（page）进行遍历；
- 检查每一行（tuple）的状态，判断其是否为可见（live tuple）或死亡（dead tuple）；
- 记录死元组的位置，准备进行清理。

### 清除死元组

- 将所有死元组标记为空闲空间；
- 如果有多余的页面可以完全清空，则将其从表中移除；
- 空间被加入到空闲空间映射（FSM）中，供后续插入操作使用。

### 清理索引（如果指定）

- 针对每个关联索引，遍历标记为死元组的主键或索引项。
- 调用索引的 `ambulkdelete()` 函数接口，批量删除已无效的索引项。

  <img src="/img/first-block.png" alt="图一" style="display:block; margin-left:auto; margin-right:auto;width:50%;" />
</figure>

PostgreSQL 会扫描目标表，建立一个死图元列表，并尽可能冻结旧元组。 该列表存储在名为maintenance_work_mem 的本地内存中。 FREEZE冻结处理将在后续的文章中介绍。扫描后，PostgreSQL 会通过引用死图元列表来删除索引图元。 图一显示了删除指向死元组的索引元组的示例。

### 更新 VM（Visibility Map）

- 标记哪些页面中的所有行对所有事务都可见；
- 有助于后续查询跳过不必要的可见性检查，提升性能。
- VM可见性是PostgreSQL事务机制的重要组成部分，后续博客将详细介绍其原理与作用。

### 更新 FSM（Free Space Map）

- 记录每个页面中可用的空闲空间大小；
- 插入新数据时，PostgreSQL 可快速找到合适的空间位置。

图二显示了更新VM和FSM后的示例：

<figure style="text-align:center;">
  <img src="/img/second-block.png" alt="图二" style="display:block; margin-left:auto; margin-right:auto;width:50%;" />
</figure>

假设表格包含三页文件。重点关注第 0 页（即第一页）。 这一页有三个元组。 Tuple_2 是一个死图元（图 一(1)）。 在这种情况下，PostgreSQL 会删除 Tuple 2 并重新排列剩余的元组，以修复碎片。 然后，它会更新该页面的 FSM 和 VM（图 一(2)）。 PostgreSQL 将继续这一过程，直到最后一页。请注意，不必要的行指针不会被删除。 它们将来会被重新使用。 这是因为如果删除了行指针，就必须更新相关索引的所有索引元组。

### 收集统计信息（如果使用了 ANALYZE）

- 分析表的列分布、NDistinct 值等；
- 更新 `pg_statistic` 系统表，供查询优化器参考。

### 冻结旧事务 ID（如果启用了 FREEZE）

- 将事务 ID 小于某个阈值的元组“冻结”，使其不再参与事务可见性判断；
- 防止事务 ID 回绕造成的数据损坏。

### VACUUM源码主要函数解析

#### VACUUM的入口函数

```c
void ExecVacuum(ParseState *pstate, VacuumStmt *vacstmt, bool isTopLevel);
```

这是 `VACUUM` 命令的主入口，功能包括：

- 解析 SQL 语句选项；
- 构建 `VacuumParams` 参数；
- 构建访问策略（`BufferAccessStrategy`）；
- 调用统一处理函数 `vacuum()` 执行实际操作。

##### 参数初始化

主要初始化 `VacuumParams` 结构体中的默认参数（如是否清理索引、是否截断页、是否并行、是否处理 TOAST 表等），包括：

```c
params.index_cleanup = VACOPTVALUE_UNSPECIFIED;
params.truncate = VACOPTVALUE_UNSPECIFIED;
params.nworkers = 0;  // 默认允许并行
ring_size = -1;       // BUFFER_USAGE_LIMIT 未指定
```

------

##### 参数解析逻辑

循环解析 `vacstmt->options`：

```c
foreach(lc, vacstmt->options)
```

常见解析分支包括：

- `verbose`：是否输出详细信息
- `skip_locked`：跳过被锁定的数据页
- `buffer_usage_limit`：设置 BAS 缓冲区使用上限（单位 kB）
- `analyze`：是否执行统计分析
- `freeze`：是否进行冻结处理
- `full`：是否为 `VACUUM FULL`
- `index_cleanup`：是否清理索引页
- `truncate`：是否截断空白页
- `parallel`：设置并行 worker 数量
- `skip_database_stats`：跳过数据库级统计信息
- `only_database_stats`：仅更新数据库级统计信息

------

##### 参数合法性校验（Sanity Checks）

包括但不限于：

- 不允许 `VACUUM FULL` 并行：

  ```c
  if ((params.options & VACOPT_FULL) && params.nworkers > 0)
  ```

- `BUFFER_USAGE_LIMIT` 不能与 `VACUUM FULL` 一起用（除非 ANALYZE 也开启）：

  ```c
  if (ring_size != -1 && (params.options & VACOPT_FULL) && !(params.options & VACOPT_ANALYZE))
  ```

- `ONLY_DATABASE_STATS` 不支持配合其他选项：

  ```c
  if (params.options & VACOPT_ONLY_DATABASE_STATS) { ... }
  ```

------

### 设置冻结相关参数（freeze age）

当启用 `FREEZE` 时，全部设为 0，否则设为 -1 表示使用默认：

```c
if (params.options & VACOPT_FREEZE)
{
    params.freeze_min_age = 0;
    ...
}
else
{
    params.freeze_min_age = -1;
    ...
}
```

------

#####  创建 Vacuum 用内存上下文

```c
vac_context = AllocSetContextCreate(PortalContext, "Vacuum", ALLOCSET_DEFAULT_SIZES);
```

这是一种跨事务使用的内存上下文（通常用于 TOAST 表或者持久结构），可在错误恢复时自动释放。

------

#####  创建 BufferAccessStrategy（BAS）

如果当前不是 `VACUUM FULL` 或 `ONLY_DATABASE_STATS`，则为 vacuum 分配一个缓冲访问策略，用于控制缓存页的替换策略（如 ring buffer）：

```c
if ((params.options & (VACOPT_ONLY_DATABASE_STATS | VACOPT_FULL)) == 0 ||
    (params.options & VACOPT_ANALYZE) != 0)
{
    MemoryContext old_context = MemoryContextSwitchTo(vac_context);
    ...
}
```

后续代码会调用：

```c
bstrategy = GetAccessStrategy(BAS_VACUUM);
```

或带 ring_size 的 BAS 策略。

#### vacuum()：统一调度函数

```c
void vacuum(List *relations, VacuumParams *params, BufferAccessStrategy bstrategy, MemoryContext vac_context, bool isTopLevel);
```

PostgreSQL 的 `vacuum()` 函数是整个清理工作的入口。无论是手动执行 `VACUUM`，还是由 autovacuum 守护进程触发，都会走到这个函数。其简要流程如下：

##### 参数检查与准备

```c
if (params->options & VACOPT_VACUUM) {
    PreventInTransactionBlock(isTopLevel, stmttype);
}
```

- `VACUUM` 不能在事务块中执行（否则事务提交不会生效）；
- `ANALYZE` 则可以在事务内外执行。

##### 防止递归调用

```c
if (in_vacuum)
    ereport(ERROR,
            errmsg("%s cannot be executed from VACUUM or ANALYZE", stmttype));
```

避免 VACUUM 或 ANALYZE 在内部调用自身，防止出现无限递归（例如恶意索引表达式）。

##### 构造要处理的关系表列表

```c
if (relations != NIL)
    relations = expand_vacuum_rel(...);
else
    relations = get_all_vacuum_rels(...);
```

- 如果明确指定表名，展开其子分区；
- 否则处理整个数据库中的相关表。

##### 确定是否使用独立事务

```c
if (params->options & VACOPT_VACUUM)
    use_own_xacts = true;
```

- VACUUM 总是使用独立事务，以便尽早释放锁；
- ANALYZE 则根据是否在事务中、是否处理多张表动态判断。

##### VACUUM/ANALYZE 循环处理每张表

```c
c复制编辑foreach(cur, relations) {
    if (params->options & VACOPT_VACUUM)
        vacuum_rel(...);

    if (params->options & VACOPT_ANALYZE)
        analyze_rel(...);
}
```

每张表都可能执行 `vacuum_rel()`（清理） 和 `analyze_rel()`（收集统计信息），二者分别有自己的子事务控制。主要职责：

- 检查语义、锁机制和事务隔离；
- 展开待处理的表（支持分区表）；
- 控制是否使用子事务处理每个表（提高容错能力）；
- 对每张表调用 `vacuum_rel()` 和 `analyze_rel()`。

该函数还通过 `PG_TRY/PG_CATCH` 实现异常处理与资源回收机制，保证系统健壮性。

#### vacuum_rel()：实际执行 VACUUM 的表级操作

- 这是 PostgreSQL 在执行 `VACUUM` 命令时处理每个表的关键函数。
- 它支持普通 VACUUM 和 `VACUUM FULL`（即 CLUSTER 重写表）的操作。
- 它可由手动执行的 `VACUUM`、自动清理任务（`autovacuum`）、或内部调用触发。

##### **事务启动与标记**

```c
StartTransactionCommand();
```

- `VACUUM` 是通过短事务逐个表执行的，避免长事务持锁过久。
- 如果不是 FULL VACUUM，会设置 `PROC_IN_VACUUM` 标志，允许其他 VACUUM 操作跳过这个进程：

```c
MyProc->statusFlags |= PROC_IN_VACUUM;
```

- 如果是因为事务 ID wraparound 被强制触发（`is_wraparound`），会额外设置 `PROC_VACUUM_FOR_WRAPAROUND`。

##### **快照与信号检测**

```c
PushActiveSnapshot(GetTransactionSnapshot());
CHECK_FOR_INTERRUPTS();
```

- 获取快照以防止事务 wraparound 等问题。
- 检查是否有 `SIGINT` 中断等外部取消请求。

------

##### **锁定与打开表**

```c
rel = vacuum_open_relation(...);
```

- 根据是否是 FULL VACUUM 决定锁的模式：
  - `VACOPT_FULL`：`AccessExclusiveLock`（强锁，阻塞所有操作）
  - 否则使用 `ShareUpdateExclusiveLock`（允许并发查询）
- 如果表不存在或锁获取失败，提前返回。

------

#####  **权限检查与 relkind 判断**

- 检查是否有权限 vacuum 该表（如只读用户无权限）：

```c
if (!vacuum_is_permitted_for_relation(...))
```

- 只支持普通表（heap）、物化视图（matview）、TOAST 表、分区表头：

```c
rel->rd_rel->relkind != RELKIND_RELATION ...
```

------

##### **跳过其他后端的临时表**

```c
if (RELATION_IS_OTHER_TEMP(rel))
```

- 忽略其他会话的临时表，因为其数据不在当前 session 中。

------

#####  **跳过分区表头节点**

```c
if (rel->rd_rel->relkind == RELKIND_PARTITIONED_TABLE)
```

- VACUUM 实际操作应应用在子分区上，父表结构无需清理。

------

#####  **获取 session-level 锁**

```c
LockRelationIdForSession(...)
```

- 为后续可能访问的 TOAST 表获取安全保障，避免 VACUUM TOAST 时父表被 drop。

------

##### **处理 reloptions（如 index_cleanup）**

- 通过表级参数设置如：
  - 是否清理索引（`index_cleanup`）
  - truncate 策略（是否截断空页）
  - eager freeze 错误容忍率等。

------

##### **TOAST 表处理策略**

```
if ((params->options & VACOPT_PROCESS_TOAST) != 0 ...)
```

- 如果指定清理 TOAST，记录 toast_relid，准备后续递归调用 `vacuum_rel()`。
- TOAST表是PostgreSQL用来处理一行元组的大小超过页面限制的机制，后续博客详细介绍。

------

##### **切换到表所有者权限**

```c
SetUserIdAndSecContext(...)
```

- 保证索引表达式、触发器等的执行具有合法权限。
- 使用 `RestrictSearchPath()` 限制 SQL 注入风险。

------

##### **执行 VACUUM 动作（核心）**

```c
c复制编辑if (params->options & VACOPT_FULL)
    cluster_rel(...);
else
    table_relation_vacuum(rel,...);
```

- FULL：重写表文件（调用 `cluster_rel()`）
- 普通 VACUUM：增量清理（调用 `table_relation_vacuum()`，内部用 `heap_vacuum()`）

#### VACUUM 中的关键机制

#### Freeze 机制与 relfrozenxid

PostgreSQL 为了避免事务 ID wraparound 会“冻结”老旧的 tuple。`relfrozenxid` 表示该表中所有 tuple 的最小 XID ≥ 此值。

关键参数：

- `vacuum_freeze_min_age`：大于此 age 的 tuple 会被冻结；
- `vacuum_freeze_table_age`：表超过此 age 会触发 aggressive vacuum；
- `autovacuum_freeze_max_age`：超过此值数据库将强制 vacuum 防止 wraparound。

#### Failsafe 模式

代码中定义：

```c
bool VacuumFailsafeActive = false;
```

如果 `relfrozenxid` 太过陈旧，系统将进入 failsafe 模式，**强制清理更多数据、跳过延迟机制**，以防止崩溃。

判断依据：

```c
vacuum_xid_failsafe_check()
```

会对比当前 `relfrozenxid` 与计算出的 `xid_skip_limit` 进行比较。

------

## VACUUM 中的资源与性能控制

### Cost-Based Delay

通过以下 GUC 参数控制 VACUUM 的资源占用：

```c
double vacuum_cost_delay;
int vacuum_cost_limit;
```

这是一种“自我节流”机制，避免 VACUUM 对系统产生过多 IO 压力。

### Ring Buffer 使用

通过参数 `BUFFER_USAGE_LIMIT` 控制 VACUUM 使用的 buffer 数量，避免污染系统共享缓冲区。

```c
bstrategy = GetAccessStrategyWithSize(BAS_VACUUM, ring_size);
```

------

## VACUUM 统计信息更新

在清理完成后，会调用：

```c
vac_update_relstats()
vac_update_datfrozenxid()
```

更新 `pg_class`、`pg_database` 中的统计信息。这些更新直接修改元组内容（非 MVCC 更新），保证 VACUUM 后不会留下无效元组，避免 VACUUM 自己污染需要 VACUUM 的元数据。

## 总结

`VACUUM` 是 PostgreSQL 中维护数据库健康的重要工具。它不仅可以回收死元组释放空间，还能优化查询性能、防止事务 ID 回绕等问题。理解其工作原理和执行流程，有助于我们更好地调优系统、设计合理的维护策略。
